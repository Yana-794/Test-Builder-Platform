## 1. Назначение документа

Документ фиксирует продуктовую концепцию Test Builder Platform, целевых пользователей, бизнес-цели, границы первой версии, основные бизнес-процессы, Use Cases, User Stories, критерии приёмки и пользовательские пути. Он служит основой для последующего проектирования API, модели данных, интерфейсов и тестирования.

Это не окончательная спецификация всех экранов и полей. Решения, которые требуют проверки на пользователях или отдельного согласования, вынесены в раздел «Открытые вопросы».

## 2. Product Vision

**Test Builder Platform — платформа для создания тестов, диагностики знаний и развития преподавательской практики.**

Платформа позволяет преподавателям, репетиторам и другим авторам тестов создавать проверочные материалы, публиковать их по ссылке или QR-коду, проводить тестирование без обязательной регистрации ученика, автоматически оценивать ответы и анализировать результаты.

Дополнительная бизнес-ценность продукта — возможность использовать открытые диагностические тесты как канал знакомства потенциальных учеников с преподавателем и получения добровольных обращений.

### 2.1. Ценностное предложение

| Пользователь | Ценность |
|---|---|
| Преподаватель / репетитор / автор тестов | Быстрее создаёт и проверяет тесты, видит проблемные вопросы и темы, организует результаты учеников, может получать обращения от заинтересованных пользователей. |
| Ученик / студент / участник теста | Быстро проходит тест без регистрации, получает результат и понимает, какие темы стоит повторить. |
| Потенциальный ученик | Может познакомиться с подходом преподавателя через открытый диагностический тест и при желании связаться с ним. |

### 2.2. Позиционирование

Продукт не является полноценной LMS, электронным журналом или маркетплейсом репетиторов. Его основное ядро — создание тестов, прохождение, оценивание и аналитика. Инструменты привлечения учеников и групповой работы усиливают это ядро.

## 3. Акторы и заинтересованные стороны

### 3.1. Основные акторы

| Актор | Описание | Аккаунт |
|---|---|---|
| Создатель тестов | Любой зарегистрированный пользователь: преподаватель, репетитор, автор курса или другой человек, которому нужно создавать тесты. Все создатели имеют одинаковый базовый набор прав. | Да |
| Участник теста | Человек, который открывает публичную ссылку и проходит тест. | Нет, для MVP |
| Потенциальный ученик / заявитель | Участник теста, который добровольно оставляет запрос на связь с создателем. | Нет |
| Внешний канал распространения | Социальная сеть, мессенджер, сайт, QR-носитель или другой канал, через который распространяется ссылка. | Вне платформы |
| Система Test Builder Platform | Проверяет доступ, хранит тесты и попытки, оценивает ответы, формирует аналитику и сохраняет обращения. | — |

**Администратор платформы не входит в пользовательскую модель MVP.** Публичная регистрация создаёт обычный аккаунт создателя тестов; пользователь не может назначить себе дополнительные привилегии.

### 3.2. Основные заинтересованные стороны

- Создатели тестов — основные заказчики и пользователи функциональности.
- Участники тестов — пользователи публичного сценария прохождения.
- Владелец продукта — определяет приоритеты, ценность и развитие платформы.
- Команда разработки — реализует и сопровождает продукт.

## 6. Бизнес-правила

| ID | Правило |
|---|---|
| RULE-01 | В MVP существует один тип зарегистрированного аккаунта — создатель тестов. Разделения на роли преподавателя и администратора нет. |
| RULE-02 | Ученик/участник не создаёт аккаунт для прохождения публичного теста. |
| RULE-03 | Черновик доступен только владельцу. Все операции над приватным объектом проверяют владельца на backend. |
| RULE-04 | Публикация является неизменяемым снимком. Изменение черновика не меняет опубликованные версии и существующие попытки. |
| RULE-05 | Каждая попытка привязана к конкретной публикации, а не к изменяемому черновику. |
| RULE-06 | Для single_choice вариант ответа должен принадлежать конкретному вопросу в конкретном снимке публикации. |
| RULE-07 | Текстовый ответ в текущем MVP сравнивается после удаления пробелов по краям и нормализации регистра. Внутренние пробелы и пунктуация не удаляются. |
| RULE-08 | Балл за вопрос не может быть отрицательным. Проверка публикации контролирует корректность структуры вопроса и правильных ответов. |
| RULE-09 | Завершение попытки и расчёт результата выполняются атомарно. Повторный submit возвращает сохранённый результат. |
| RULE-10 | Публичный DTO теста не содержит correctTextAnswer, isCorrect и других данных, позволяющих раскрыть правильный ответ. |
| RULE-11 | Контактные данные передаются создателю только после явного действия и согласия участника. Собираются только данные, необходимые для обратной связи. |
| RULE-12 | Имя участника само по себе не является надёжным идентификатором одного и того же человека между разными попытками. |
| RULE-13 | В групповой версии анонимная попытка может быть привязана к назначению теста через отдельную ссылку/токен назначения. Для достоверной межсессионной идентификации потребуется отдельное решение. |
| RULE-14 | Результаты, тесты, группы и обращения одного создателя недоступны другим создателям. |

## 7. Границы продукта и релизов

### 7.1. MVP — обязательное ядро

- Регистрация, вход, выход и проверка сессии создателя.
- Личный кабинет со списком тестов.
- Создание и редактирование теста, явное сохранение черновика.
- Вопросы single_choice и text, варианты ответов, баллы и порядок.
- Предварительный просмотр и проверка теста перед публикацией.
- Публикация неизменяемого снимка, уникальная ссылка и QR.
- Публичное прохождение без регистрации.
- Автоматическая проверка, сохранение результата и защита от повторной отправки.
- Базовая аналитика теста и вопросов.

### 7.2. MVP+ — бизнес-ценность

- Диагностический тип/признак теста, предмет, уровень и темы.
- Необязательный CTA после результата.
- Добровольная форма контактного обращения с согласием.
- Уведомление/список обращений в кабинете создателя.
- Публичная страница создателя.
- События открытия, начала и завершения теста с понятными определениями метрик.

### 7.3. Следующий релиз

- Группы учеников.
- Назначения опубликованных версий тестов группам.
- Ссылки/коды назначения и агрегированная аналитика группы.
- История результатов по участнику — только при наличии надёжного механизма идентификации.

### 7.4. За пределами текущего продукта

- Маркетплейс репетиторов и распределение заказов.
- Видеозвонки, расписание и приём оплаты за занятия.
- Полноценная LMS и электронный журнал.
- Обязательные аккаунты учеников.
- Социальная сеть преподавателей.

### UC-01. Зарегистрировать аккаунт создателя

**Цель:** предоставить новому пользователю доступ к личному кабинету и созданию тестов.  
**Актор:** незарегистрированный пользователь.  
**Предусловия:** пользователь не авторизован.  
**Триггер:** пользователь выбирает «Зарегистрироваться».

**Основной сценарий:**
1. Система отображает форму регистрации.
2. Пользователь вводит email, отображаемое имя и пароль.
3. Система проверяет формат и обязательность полей, политику пароля и допустимость регистрации.
4. Система проверяет уникальность email.
5. Система сохраняет аккаунт с безопасным хешем пароля.
6. Система сообщает об успешной регистрации и предлагает войти либо выполняет согласованный сценарий входа.

**Альтернативы и ошибки:**
- A1: email уже зарегистрирован — система не создаёт второй аккаунт и показывает безопасное сообщение.
- A2: данные невалидны — система возвращает ошибки конкретных полей.
- A3: ошибка БД/сервиса — система не создаёт частично сохранённый аккаунт и показывает общую ошибку.

**Постусловия:** создан один аккаунт создателя; пароль не хранится в открытом виде.

### UC-02. Войти и завершить сессию

**Цель:** предоставить владельцу доступ к его тестам и аналитике.  
**Актор:** зарегистрированный создатель.  
**Предусловия:** аккаунт существует; для входа аккаунт допускает аутентификацию.  
**Триггер:** пользователь отправляет форму входа.

**Основной сценарий входа:**
1. Пользователь вводит email и пароль.
2. Система находит аккаунт и проверяет пароль.
3. Система создаёт случайный серверный идентификатор сессии.
4. Система сохраняет хеш токена сессии и срок действия.
5. Браузер получает HttpOnly-cookie с настроенными атрибутами безопасности.
6. Система возвращает безопасный профиль пользователя и CSRF-токен для последующих изменяющих запросов.

**Альтернативы:** неверные учётные данные приводят к одинаковому сообщению без раскрытия существования email; истёкшая/отозванная сессия не даёт доступа; выход отзывает сессию на сервере и очищает cookie.

**Постусловия:** при успешном входе существует действующая серверная сессия; после выхода токен больше не авторизует запросы.

### UC-03. Создать и редактировать тест

**Цель:** подготовить тест для последующей публикации.  
**Актор:** авторизованный создатель.  
**Предусловия:** действующая сессия.  
**Триггер:** пользователь выбирает «Создать тест».

**Основной сценарий:**
1. Система создаёт черновик, принадлежащий текущему пользователю.
2. Пользователь задаёт название и описание.
3. Пользователь добавляет вопросы типа single_choice или text.
4. Для single_choice пользователь задаёт варианты и один правильный вариант.
5. Для text пользователь задаёт ожидаемый текстовый ответ.
6. Пользователь указывает баллы и порядок вопросов.
7. Пользователь явно нажимает «Сохранить».
8. Система валидирует данные и сохраняет изменения.

**Альтернативы:** невалидные данные не сохраняются; чужой testId не даёт читать или изменять тест; конфликт/ошибка сохранения отображается без ложного сообщения об успешном сохранении.

**Постусловия:** черновик сохранён и доступен только владельцу.

### UC-04. Проверить и опубликовать тест

**Цель:** создать доступную участникам неизменяемую версию теста.  
**Актор:** авторизованный создатель.  
**Предусловия:** существует сохранённый черновик, доступный текущему владельцу.  
**Триггер:** пользователь нажимает «Опубликовать».

**Основной сценарий:**
1. Система проверяет владельца и актуальность черновика.
2. Система проверяет название, наличие вопросов и корректность каждого типа вопроса.
3. Система проверяет баллы и наличие положительного максимального балла для оцениваемого теста.
4. Если ошибок нет, система в одной транзакции создаёт новый снимок публикации и обновляет указатель текущей опубликованной версии теста.
5. Система генерирует уникальный публичный токен и формирует ссылку/QR.
6. Система возвращает метаданные публикации и ссылку.

**Альтернативы:** при ошибках валидации публикация не создаётся; при сбое транзакции не должно оставаться частичной публикации; повторный запрос не должен создавать неконтролируемые дубликаты при наличии механизма идемпотентности.

**Постусловия:** опубликованная версия неизменяема; последующие изменения черновика создают новую версию при следующей публикации.

### UC-05. Получить ссылку и распространить тест

**Цель:** дать возможность привлечь участников из внешних каналов.  
**Актор:** создатель.  
**Предусловия:** у теста есть опубликованная версия.  
**Основной сценарий:** пользователь копирует публичную ссылку или QR-код и отправляет её через внешний канал.

**Постусловия:** ссылка доступна участникам, которым она передана. Платформа не гарантирует количество просмотров или новых учеников.

### UC-06. Пройти публичный тест

**Цель:** позволить человеку пройти тест без создания аккаунта.  
**Актор:** участник теста.  
**Предусловия:** опубликованная версия доступна по ссылке.  
**Основной сценарий:**
1. Участник открывает публичную ссылку.
2. Система находит публикацию по публичному токену.
3. Система отдаёт Public DTO без правильных ответов.
4. Участник вводит отображаемое имя.
5. Система создаёт попытку и отдельный секрет доступа к ней.
6. Участник отвечает на вопросы и отправляет ответы.

**Альтернативы:** несуществующая ссылка возвращает 404; недоступная публикация показывает понятное сообщение; некорректные или чужие идентификаторы ответов отклоняются.

### UC-07. Получить результат и сохранить попытку

**Цель:** корректно оценить работу и сохранить историю прохождения.  
**Акторы:** участник и система.  
**Предусловия:** существует незавершённая попытка, связанная с конкретной публикацией.  
**Основной сценарий:**
1. Backend получает ответы и проверяет их принадлежность вопросам/вариантам в снимке.
2. Для single_choice начисляет баллы за выбранный правильный вариант.
3. Для text сравнивает ответ после удаления пробелов по краям и нормализации регистра; внутренние пробелы и пунктуацию сохраняет.
4. В одной транзакции фиксирует ответы, баллы и итог попытки.
5. Повторная отправка завершённой попытки возвращает ранее сохранённый результат.
6. Участник получает результат; создатель видит сохранённую попытку в аналитике.

**Постусловия:** попытка завершена ровно один раз; результат не зависит от дальнейших изменений черновика.

### UC-08. Просмотреть аналитику теста

**Цель:** понять результаты участников и сложность вопросов.  
**Актор:** создатель.  
**Предусловия:** действующая сессия; тест принадлежит создателю.  
**Основной сценарий:** система показывает число завершённых попыток, средний процент, распределение результатов и статистику по вопросам. Создатель может перейти к деталям отдельной попытки.

**Ограничения:** аналитика не должна раскрывать данные другого владельца; персональные данные отображаются только в объёме, необходимом создателю для работы с его тестом.

### UC-09. Оставить запрос на связь с создателем

**Цель:** дать заинтересованному участнику возможность добровольно запросить контакт.  
**Актор:** участник диагностического теста.  
**Предусловия:** для теста настроен CTA; создатель указал допустимый способ связи.  
**Основной сценарий:** после результата участник выбирает «Связаться», видит объяснение, какие данные и кому будут переданы, вводит необходимые контактные данные, отмечает отдельное согласие и отправляет форму. Система сохраняет обращение, связывает его с тестом/попыткой и показывает создателю в кабинете.

**Альтернативы:** отказ от согласия не создаёт обращение; недействительные данные не сохраняются; повторная отправка должна обрабатываться контролируемо.

**Постусловия:** обращение сохранено только при наличии требуемого согласия. Отправка заявки не означает гарантированное получение услуги.

### UC-10. Управлять группами и назначать тесты (следующий релиз)

**Цель:** организовать регулярную работу с несколькими учениками.  
**Актор:** создатель.  
**Основной сценарий:** создатель создаёт группу, задаёт название, создаёт назначение на конкретную опубликованную версию теста, получает отдельную ссылку/код назначения и передаёт его участникам. Попытки по этой ссылке связываются с назначением и используются в агрегированной аналитике группы.

**Ограничение:** без аккаунтов или устойчивых персональных идентификаторов нельзя достоверно объединять попытки одного человека между разными назначениями. Имя участника не является уникальным ключом.

### 9.3. User Stories и Acceptance Criteria

#### Epic A. Доступ и аккаунт

**US-01 — Регистрация**  
Как новый пользователь, я хочу зарегистрироваться по email и паролю, чтобы создавать и хранить собственные тесты.

Критерии приёмки:
- Given незарегистрированный пользователь, when он отправляет валидные обязательные поля, then создаётся один аккаунт создателя.
- Given email уже используется, when пользователь пытается зарегистрироваться повторно, then второй аккаунт не создаётся.
- Пароль не сохраняется и не возвращается в открытом виде.
- Поля role/ownerId/status не принимаются как клиентские управляющие данные.

**US-02 — Вход и выход**  
Как зарегистрированный пользователь, я хочу входить и выходить из личного кабинета, чтобы защищать доступ к своим материалам.

Критерии приёмки:
- При корректных данных создаётся серверная сессия и устанавливается защищённая cookie.
- При неверных данных возвращается одинаковая общая ошибка для неизвестного email и неверного пароля.
- GET /auth/me возвращает текущего пользователя при действующей сессии и 401 без неё.
- Logout отзывает сессию на сервере; прежний cookie больше не даёт доступ.
- Изменяющие запросы с cookie проходят CSRF- и Origin-проверки.

#### Epic B. Создание теста

**US-03 — Создать черновик**  
Как создатель, я хочу создать тест и сохранить его черновик, чтобы продолжить работу позже.

Критерии приёмки:
- Черновик автоматически принадлежит текущему пользователю, определённому по сессии.
- Сохранение происходит по явному действию пользователя.
- Список и детали тестов доступны только владельцу.

**US-04 — Добавить вопрос с выбором ответа**  
Как создатель, я хочу добавить вопрос с несколькими вариантами и одним правильным ответом, чтобы автоматически проверять знания.

Критерии приёмки:
- Вопрос имеет текст, тип, баллы и позицию.
- Варианты принадлежат конкретному вопросу.
- Для публикации требуется не менее двух непустых вариантов и ровно один правильный вариант.

**US-05 — Добавить текстовый вопрос**  
Как создатель, я хочу задать эталонный текстовый ответ, чтобы проверять короткие текстовые ответы автоматически.

Критерии приёмки:
- У текстового вопроса задан эталонный ответ.
- При проверке удаляются пробелы по краям и нормализуется регистр.
- Внутренние пробелы и пунктуация сохраняются.

**US-06 — Изменить порядок вопросов**  
Как создатель, я хочу менять порядок вопросов, чтобы выстраивать тест в нужной последовательности.

Критерии приёмки:
- Система принимает только полный набор идентификаторов вопросов текущего теста без повторов и пропусков.
- Новые позиции сохраняются атомарно.

#### Epic C. Публикация и распространение

**US-07 — Проверить готовность теста**  
Как создатель, я хочу увидеть ошибки до публикации, чтобы не отправлять участникам незавершённый тест.

Критерии приёмки:
- Проверяются название, наличие вопросов, корректность типов, варианты, правильные ответы и баллы.
- При ошибках система показывает список проблем с привязкой к вопросу/полю.
- Невалидный тест не публикуется.

**US-08 — Опубликовать версию**  
Как создатель, я хочу опубликовать готовый тест, чтобы участники могли пройти его по ссылке.

Критерии приёмки:
- Публикация создаёт отдельный неизменяемый snapshot.
- Попытка привязана к ID публикации.
- Изменение черновика не меняет существующие публикации и попытки.
- Публичная ссылка использует непредсказуемый токен.

**US-09 — Получить ссылку и QR**  
Как создатель, я хочу скопировать ссылку или показать QR-код, чтобы распространить тест во внешних каналах.

Критерии приёмки:
- Ссылка открывает публичную опубликованную версию.
- QR кодирует ту же ссылку.
- Приватные данные и ключи правильных ответов не включаются в ссылку или QR.

#### Epic D. Прохождение и оценивание

**US-10 — Пройти тест без регистрации**  
Как участник, я хочу открыть тест по ссылке и пройти его без аккаунта, чтобы не тратить время на регистрацию.

Критерии приёмки:
- Публичный endpoint отдаёт только поля, необходимые для отображения теста.
- В публичном DTO нет правильных ответов и признаков isCorrect.
- Перед началом попытки участник вводит допустимое отображаемое имя.
- Доступ к созданной попытке защищён отдельным секретом, а не только UUID.

**US-11 — Отправить ответы и получить результат**  
Как участник, я хочу отправить ответы и получить результат, чтобы понять свой текущий уровень.

Критерии приёмки:
- Backend проверяет принадлежность вопроса и варианта конкретному snapshot.
- Оценивание выполняется на сервере.
- Завершение попытки и сохранение ответов/баллов выполняются транзакционно.
- Повторная или параллельная отправка не начисляет баллы повторно и возвращает сохранённый результат.

#### Epic E. Аналитика

**US-12 — Посмотреть общую статистику**  
Как создатель, я хочу видеть количество попыток и средний результат, чтобы оценивать эффективность теста.

Критерии приёмки:
- В расчёты включаются только завершённые попытки, если метрика явно не определяет другое.
- Для сравнения тестов с разным максимумом используется процент, а не только абсолютные баллы.
- Доступ к аналитике проверяет владельца теста.

**US-13 — Проанализировать вопросы**  
Как создатель, я хочу видеть долю правильных ответов по каждому вопросу, чтобы находить сложные темы и формулировки.

Критерии приёмки:
- Статистика рассчитывается по завершённым попыткам соответствующей публикации.
- В знаменатель попадают только валидные ответы на конкретный вопрос.
- Показатели не смешивают ответы разных версий теста без явного правила сопоставления.

#### Epic F. Привлечение и обращения

**US-14 — Настроить диагностический тест**  
Как преподаватель, я хочу пометить тест как диагностический и указать предмет/уровень/темы, чтобы участник понимал назначение теста.

Критерии приёмки:
- Метаданные отображаются на публичной странице.
- Результаты могут агрегироваться по указанным темам.
- Диагностическая маркировка не меняет правила оценивания.

**US-15 — Оставить запрос на связь**  
Как заинтересованный участник, я хочу добровольно оставить контакт после результата, чтобы преподаватель мог связаться со мной.

Критерии приёмки:
- Форма явно объясняет, кому и какие данные будут переданы.
- Согласие не предустановлено и является отдельным действием.
- Без согласия контактный запрос не создаётся.
- В обращении сохраняются источник/тест/время и версия текста согласия, если это предусмотрено утверждённой политикой.
- Создатель видит только обращения к своим тестам.

#### Epic G. Группы — следующий релиз

**US-16 — Создать группу**  
Как преподаватель, я хочу создавать собственные группы, чтобы организовывать регулярную работу с учениками.

**US-17 — Назначить тест группе**  
Как преподаватель, я хочу назначить опубликованную версию теста группе, чтобы все участники проходили одну и ту же версию.

**US-18 — Посмотреть аналитику группы**  
Как преподаватель, я хочу видеть агрегированные результаты группы, чтобы понимать общие пробелы в знаниях.

Критерии для группового функционала должны дополнительно определить механизм идентификации участника. Имя, вводимое вручную, не гарантирует объединение попыток одного человека.

## 11. BPMN: сквозной бизнес-процесс

Отдельный файл `bpmn/test-builder-platform-main-process.bpmn` содержит BPMN 2.0 Collaboration с тремя участниками:

1. **Создатель теста** — готовит черновик, отправляет на публикацию и распространяет ссылку.
2. **Test Builder Platform** — проверяет владельца и содержимое, создаёт snapshot, выдаёт публичную версию, принимает и оценивает попытки, сохраняет добровольные обращения.
3. **Участник теста** — открывает ссылку, проходит тест, получает результат и при желании оставляет обращение.

### 11.1. Процесс публикации

1. Создатель формирует и сохраняет черновик.
2. Отправляет запрос на публикацию.
3. Платформа проверяет права владельца.
4. Платформа валидирует содержимое.
5. XOR Gateway «Тест валиден?» разделяет поток:
   - Нет — платформа возвращает ошибки, создатель исправляет тест и повторяет публикацию.
   - Да — платформа транзакционно создаёт неизменяемый snapshot, генерирует токен ссылки и QR, возвращает результат.
6. Создатель распространяет ссылку.

### 11.2. Процесс прохождения теста

1. Участник открывает публичную ссылку.
2. Платформа загружает опубликованный snapshot и формирует публичный DTO без ключей ответов.
3. Участник указывает имя, отвечает на вопросы и отправляет ответы.
4. Платформа проверяет принадлежность questionId/optionId конкретной публикации.
5. XOR Gateway «Ответы валидны?»:
   - Нет — возвращается ошибка, участник может исправить ответы.
   - Да — платформа в транзакции оценивает ответы и завершает попытку.
6. Платформа возвращает сохранённый результат.
7. Создатель видит завершённую попытку в аналитике.

### 11.3. Процесс получения обращения

1. После результата участник выбирает действие «Связаться с создателем».
2. Система объясняет, какие данные будут переданы и кому.
3. Участник явно подтверждает согласие и отправляет форму.
4. Платформа проверяет полноту согласия и допустимость данных.
5. Обращение связывается с тестом и попыткой и показывается создателю.
6. Если участник не согласен, контактные данные не передаются и обращение не создаётся.

### 11.4. BPMN-элементы в модели

| BPMN-элемент | Применение |
|---|---|
| Participant / Pool | Создатель, платформа, участник |
| User Task | Создать тест, ввести имя, ответить, посмотреть результат |
| Service Task | Проверить права, создать snapshot, оценить попытку, сохранить обращение |
| Business Rule Task | Проверить бизнес-правила публикации |
| Message Start Event / Message Flow | Запуск обработки платформой по запросу создателя/участника |
| Intermediate Message Catch Event | Ожидание ответа платформы |
| Exclusive Gateway (XOR) | Валидность теста, принятие ответов, согласие на передачу контакта |
| End Event | Завершение публикации, прохождения или обработки обращения |

## 12. Нефункциональные требования

| ID | Область | Требование |
|---|---|---|
| NFR-01 | Безопасность паролей | Пароли хранятся только в виде стойких password hashes; открытые пароли не логируются и не возвращаются клиенту. |
| NFR-02 | Сессии | Используются серверные сессии в HttpOnly-cookie; токен хранится в БД в виде хеша; есть срок действия и отзыв. |
| NFR-03 | CSRF/CORS | Для cookie-аутентификации защищаются изменяющие запросы; CORS ограничен доверенным origin. |
| NFR-04 | Авторизация | Каждая приватная операция проверяет владельца ресурса на backend. |
| NFR-05 | Защита ответов | Публичный API не раскрывает правильные ответы и внутренние поля модели. |
| NFR-06 | Целостность | Публикация и завершение попытки выполняются транзакционно; submit идемпотентен. |
| NFR-07 | Валидация | Backend валидирует типы, размеры, допустимые идентификаторы и бизнес-ограничения. |
| NFR-08 | Доступность данных | Предусмотрены резервное копирование БД и проверяемая процедура восстановления. |
| NFR-09 | Приватность | Сбор персональных данных минимален; контакт передаётся только после явного согласия; срок хранения и удаление данных должны быть определены отдельной политикой. |
| NFR-10 | Наблюдаемость | Логи не содержат паролей, токенов, cookie, секретов и полного содержимого приватных ответов без необходимости. |

## 13. Открытые вопросы и решения, требующие согласования

| ID | Вопрос | Почему важно | Рекомендуемое решение для MVP |
|---|---|---|---|
| OQ-01 | Может ли ученик видеть правильные ответы после завершения? | Влияет на Public Result DTO и анти-списывание. | По умолчанию показывать балл/процент; раскрытие ключей включать отдельной настройкой после обсуждения. |
| OQ-02 | Какие поля содержит контактная форма? | Влияет на приватность и конверсию. | Минимум: имя, один контактный канал, текст согласия; конкретный канал определить по пилоту. |
| OQ-03 | Обязательна ли верификация email? | Влияет на регистрацию и восстановление доступа. | Решить до публичного запуска; для пилота можно отделить регистрацию от подтверждения. |
| OQ-04 | Какие диагностические уровни и предметы поддерживаются? | Влияет на каталогизацию и аналитику. | В MVP+ сначала свободные метки/справочник без сложной таксономии. |
| OQ-05 | Как идентифицировать одного ученика между попытками? | Имя не уникально; без идентификатора нельзя корректно считать индивидуальную динамику. | В MVP не обещать индивидуальную историю; в групповом релизе исследовать персональные коды/приглашения. |
| OQ-06 | Как назначать тест группе без регистрации ученика? | Нужна связь попытки с назначением. | Использовать уникальный токен назначения; отдельно определить контроль повторных прохождений. |
| OQ-07 | Как долго хранить попытки и контактные заявки? | Влияет на приватность и эксплуатацию. | Установить политику хранения до запуска с учётом целевого рынка и требований законодательства. |
| OQ-08 | Разрешить ли несколько правильных вариантов или частичное оценивание? | Текущий MVP заявляет single_choice с одним правильным вариантом и text. | Не расширять до отдельного требования; зафиксировать один правильный вариант и полные баллы. |

## 14. Рекомендуемый порядок дальнейшей аналитики и разработки

1. Согласовать открытые вопросы OQ-01—OQ-08 и окончательные границы MVP.
2. Детализировать UC-01/UC-02 и их API-контракты; реализовать и протестировать авторизацию.
3. Детализировать UC-03/UC-04: модель теста, валидация, snapshot и публикация.
4. Детализировать UC-06/UC-07: публичный DTO, попытка, защита доступа и транзакционное оценивание.
5. Детализировать UC-08: определения метрик и аналитические запросы.
6. Проверить гипотезу диагностических тестов и обращений на интервью/пилоте до реализации MVP+.
7. Проектировать группы только после проверки потребности и механизма идентификации участников.

## 15. Глоссарий

| Термин | Определение |
|---|---|
| Создатель | Зарегистрированный пользователь, который создаёт тесты. |
| Участник | Человек, проходящий публичный тест без аккаунта. |
| Черновик | Изменяемая версия теста до публикации. |
| Публикация / snapshot | Неизменяемый снимок содержимого теста с версией и публичным токеном. |
| Попытка (attempt) | Конкретное прохождение конкретной публикации одним участником. |
| Диагностический тест | Тест, предназначенный для предварительной оценки уровня/тем знаний. |
| Контактное обращение (lead) | Добровольный запрос участника на связь с создателем. |
| Назначение теста | Связь опубликованной версии с группой или другим набором участников. |
| User Story Map | Карта пользовательских действий и историй, распределённых по релизным срезам. |
